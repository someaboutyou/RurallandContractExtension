## 一、结论速览

> 你的前提是"页面修改可撤回、保存后会记录 `survey_change_diffs`、而且保证能撤回"。
> **实测下来这个前提不成立**，有三条需要先对齐：

| 前提 | 实际情况 |
| --- | --- |
| 「页面修改可撤回」 | ❌ 只有 **6 类操作型变更**有撤回入口；**表单字段、成员增删、新增地块都没有**，只能手工改回 |
| 「保存后记录 `survey_change_diffs`」 | ⚠️ 记录的是**净差异快照**（当前 result vs 原始 base），**每次保存全删重建**，不是操作流水；改回原值差异行会消失 |
| 「保证能撤回」 | ❌ **撤回地块移除 100% 报 500**；分户产生的差异记录完全缺失 |

发现 4 个 P0/P1 缺陷 + 4 个 P2 问题，其中 **1 个是"直接不可用"级别**。

## 三、`survey_change_diffs` 的真实语义（重要）

`changes.py::_rebuild_diffs()` 每次保存时：

1. **先删除**该户全部 `contractor` / `issuer` / `member` / `parcel` / `parcel_relation` 差异行；
2. 再按 `base（快照表 survey_cbf_base / survey_cbf_jtcy_base / …）` 与 `result（结果表）` **逐字段重算**。

⇒ 它是「**当前与原始基线的净差异快照**」，不是「本次保存做了什么」的日志。

**实测印证**（T1 / T2）：把承包方名称改成 X → 保存 → 差异出现；再改回原名 → 保存 → **该差异行消失**。
删掉一个"本轮才建、base 里本来没有"的成员 → **不产生"删除成员"差异**（净零变化）。

需要"操作流水"的是另一张表：`survey_change_records`（每次保存/操作一条，含 `before_summary` / `after_summary`），
它带 `change_status`（`surveyed` / `rolled_back`），撤回就是把对应记录标记为 `rolled_back`。

## 四、问题清单

### 🔴 P0-1 「撤回已保存的地块移除」100% 崩溃（500）

| 项 | 内容 |
| --- | --- |
| 位置 | `backend/app/services/survey/parcel_ops.py:1084-1087`，函数 `rollback_remove_parcel` |
| 现象 | 前端「地块信息 → 行内 → 撤回移除」每次都报错 |
| 根因 | 该函数在 `_create_change_record(...)` 的参数里引用了 `previous_result_status` / `previous_change_type` / `previous_change_reason` / `previous_is_changed` —— 这四个变量**只在兄弟函数 `remove_parcel`（:959-962）里定义过，没有搬过来**，函数体内从未赋值 ⇒ Python 当作全局名去查 ⇒ `NameError` |
| 调用链 | `PUT /results/{uid}` → `update_result:290` → `_apply_pending_operations:815` → `rollback_remove_parcel:1084` |
| 副作用 | 因为异常发生在 `db.commit()` 之前，**整次保存全部回滚**（地块移除也没生效、变更记录未被标记 `rolled_back`）—— 用户看到的是"点了撤回，报个错，什么都没变" |

**证据 1（运行时，后端日志）**

```
File ".../app/services/survey/changes.py", line 815, in _apply_pending_operations
    self.rollback_remove_parcel(
File ".../app/services/survey/parcel_ops.py", line 1084, in rollback_remove_parcel
    "restored_result_status": previous_result_status,
                              ^^^^^^^^^^^^^^^^^^^^^^
NameError: name 'previous_result_status' is not defined
```

**证据 2（静态，可复跑）**

```
$ python scripts/_static_undefined_names.py
[FAIL] parcel_ops.py::rollback_remove_parcel  未定义引用：
        L1084  previous_result_status
        L1085  previous_change_type
        L1086  previous_change_reason
        L1087  previous_is_changed
```

**修复方向**：在 `rollback_remove_parcel` 里补上这四个变量 —— 语义应取自 `before_summary` 的
`source_*` 字段（对照 `remove_parcel` 写入的 `before_summary`：`source_result_status` / `source_change_type` /
`source_change_reason` / `source_is_changed`），或用前端 payload 传来的同名值：

```python
previous_result_status = str(before_summary.get("source_result_status") or "normal").strip() or "normal"
previous_change_type = str(before_summary.get("source_change_type") or "none").strip() or "none"
previous_change_reason = before_summary.get("source_change_reason")
previous_is_changed = bool(before_summary.get("source_is_changed"))
```

（旧实现 `services/survey_service.py.bak:5209-5212` 里就是这么写的，可以对拍。）

### 🟠 P1-2 分户后 `survey_change_diffs` 完全不记录分户变更

| 项 | 内容 |
| --- | --- |
| 位置 | `backend/app/services/survey/household.py:756-764`（`split_household`） |
| 根因 | `if not commit: db.flush(); return {"queued": True}` 排在 `self._rebuild_contractor_diffs(...)` **之前** ⇒ 走"待保存操作"通道（`commit=False`）时**永远不重建差异**；而 `result.py:291` 对 `terminal_operation_types`（deregister / split / merge）**整段跳过**差异重建，没有任何补偿 |
| 不对称点 | **合户**在 `commit` 判断**之前**就重建了（`household.py:1103`）；**注销**是自己在函数里手工 `db.add(SurveyChangeDiff)` —— 只有分户漏了 |

**实测证据（T5）**

```
分户前原户 diffs=11
分户后原户 diffs=11      ← 一条没变，还是分户前的旧值
原户 resultStatus=cancelled changeType=split_household
新户 321324100001029911 diffs=0
新户 321324100001029912 diffs=0   ← 分户生成的新户，差异表里空空如也
```

**影响**：分户后点「查看变化详情」，看到的还是分户前的字段差异；新户看不到任何"我来自分户"的记录。

**修复方向**：把 `_rebuild_contractor_diffs(db, batch_id, [contractor_uid, *child_uids], change_ids=…)`
移到 `if not commit` 之前（与 `merge_household` 对齐）。

### 🟠 P1-3 承包方名称 / 编码的修改永远进不了差异表

| 项 | 内容 |
| --- | --- |
| 位置 | `backend/app/services/survey/result.py:322-329`（`update_result`） |
| 根因 | `survey_cbf_base` 这一行**同时充当快照(base)和任务行(task)**。保存时执行 `task.cbfbm = result.cbfbm; task.cbfmc = result.cbfmc`，**把基准快照覆写成当前值**；而重建差异的 `_rebuild_contractor_diffs` 在 `:331` 才跑 ⇒ 比较时 `base.cbfmc` 已经等于 `result.cbfmc`，`contractor_fields` 里的 `cbfbm/cbfmc` **恒等**，差异永不产生 |
| 实测 | T1：把「验收临时户A」改成「验收临时户改名」，保存 200，但差异表里**没有** `cbfmc` 行（只有 `cbfcysl` / 成员行）；改回原名差异同样无该行 |

**影响**：
1. 「查看变化详情」看不到承包方名称变更（名称是最常改的字段之一）；
2. 反向说明：base 快照被就地污染 ⇒ 该户"原始状态"不可再追溯。

**修复方向**：二者选一 —— ① 不再覆写 `base.cbfbm/cbfmc`（任务行字段应放独立列或另一张表）；
② 或把 `_rebuild_contractor_diffs` 提到这段覆写**之前**执行。

## 五、实测结果总表

| 用例 | 结论 | 说明 |
| --- | --- | --- |
| T1 表单改字段 → 差异 → 改回 | ✅/❌ | 差异的"产生 + 改回即消失"符合净差异语义 ✅；但 **`cbfmc` 改名不进差异** ❌（P1-3） |
| T2 成员增删 → 差异 | ✅ | 新增成员产生「新增成员」；删掉 base 中不存在的成员不产生差异（净零，符合语义） |
| T2b 真实户删成员 → 差异 → 原样恢复 | ✅ | 「删除成员」出现 → 恢复 → 消失；成员 uid 集合完全还原 |
| T3 新增地块 ×3 → 差异 | ✅ | 「新增地块」+「新增地块关联」各 3 条 |
| T4 移除地块 → 差异 → **撤回移除** | ❌ | 移除本身成功、变更记录生成；**撤回返回 500（NameError）**，事务整体回滚 |
| T5 分户 → 差异是否重建 | ❌ | 原户停在 11 条旧差异；两个新户均为 0 条（P1-2） |
| T6 注销 → 差异 → 撤回注销 | ✅ | 差异出现「承包方状态」；撤回后状态与差异**完整回到基线** |
| T7 确认调查结果 | ✅ | 确认后 `surveyStatus=confirmed`，再保存被拒 400「调查成果已确认，不能继续编辑」 |
| T8 删户残留 | ❌ | 删户后地块编码仍被占用（P1-4） |

**未实测**：撤回切割 / 撤回互换 / 撤回合户（需要几何数据与多户联动）。静态分析未发现这三条链路的
同类缺陷（都正确调用 `_rebuild_contractor_diffs`，且无未定义变量），但建议在修复 P0-1 后一并回归。

### 8.3 P1-3 当时只修了一半（已于第十一章按方案 A 彻底修完）

改回  →  1 条  (验收临时户A-改名验证 → 验收临时户A)   ← 期望 0 条

**根因是结构性的**：`survey_cbf_base` 一张表兼两个职责 ——

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| **A** | `base.cbfbm/cbfmc` 不再同步；`list_tasks` 显示改取 `result` 的值（`_serialize_task` **已经**查到了 result，只需改 2 行）；筛选/搜索仍走 base（改名后按新码搜不到） | 改动集中在 `task.py`，筛选口径留残留 |
| **B** | 维持现状，把差异语义显式定义为「相对上一次保存」 | 无需改代码，但与注销/成员等维度的"相对基线"语义不一致 |

### 9.3 新发现缺陷 P1-5：切割「本批次新增的地块」后，撤回切割在界面上失效

**现象**：保存切割后**关闭并重新打开**调查录入对话框，「撤回已保存切割」点不动 ——
`handleRollbackSavedSplit` 找不到源地块，直接提示「当前页面地块状态已变化，请先重新打开调查录入后再试」。

**证据链**：

1. 切割实现（`parcel_ops.py::split_parcel`，:465-467）会**物理删除**原地块与关联行：
   ```python
   # result 表只保存当前有效数据；源地块的完整内容已经进入变更快照。
   db.delete(old_relation)
   db.delete(old_parcel)
   ```
   实测：切割后 `survey_dk_result` 与 `survey_cbdkxx_result` 中该 `dkbm` **查无行**（不是 `split_source`）。
2. 全后端**没有任何一处**把 `result_status` 写成 `split_source` —— 它只是查询过滤条件与返回时的虚拟标记。
3. 列表服务（`land_parcel_service.py:213`）的 `historical_split_rows`（按 `split_source` 过滤）**恒为空分支**。
4. 兜底分支（:283-288）决定了分水岭：
   ```python
   relation_source = base_relation or fallback_relation
   if relation_source is None:
       continue          # ← 直接跳过这个 dkbm
   ```
   - 切割**批次基线里的地块** → `survey_cbdkxx_base` 有行 → 返回 `resultStatus="split_source"` 的虚拟条目 → 前端撤回**可用** ✅
   - 切割**本批次新增的地块**（`added`，base 里没有）+ result 表行又被删 → **跳过** → 前端拿不到 → 撤回**失效** ❌
5. 前端（`ContractorResultDialog.vue:611`）依赖该条目定位：
   ```js
   const sourceParcel = parcels.value.find(i => i.dkbm === change.originalDkbm && i.resultStatus === "split_source");
   if (!sourceParcel) { ElMessage.warning("当前页面地块状态已变化……"); return; }
   ```

**影响面**：影响「先新增地块、再切割它、保存后重开」这条真实路径。后端撤回能力本身是好的
（S2 直接下发 `rollback_split_parcel` 得到 200 且状态完整还原），**坏的只是界面入口的定位逻辑**。

**修复方向（二选一，供决策）**：

- **A（推荐，改后端兜底）**：`get_survey_parcels` 在 `relation_source is None` 时，改为从变更快照

  改动局限在一个函数，不动切割的存储语义。
- **B（改存储语义）**：`split_parcel` 不删除原行，改为标记 `result_status='split_source'`。
  语义更直观，但会改动既有 `dk_result` 存量数据口径（"result 表只保存当前有效数据"是现设计前提），回归面较大。

### 11.2 为什么必须"不覆写 base"——两个被排除的替代方案

P1-3 上一轮只做到"改名能进差异表"，但**净差异语义仍破**：改名产生 1 条，改回原值不是"差异消失"，而是又比出一条（before/after 互换）。根因是 `survey_cbf_base` 一张表**同时**承担两个角色：

- **批次基线快照**（`_rebuild_diffs` 拿它当 `before`）；
- **任务表**（`list_tasks` 直接读它的 `cbfbm/cbfmc` 做筛选、排序与显示）。

保存时把 `cbfbm/cbfmc` 同步成当前值，基线就被**永久推进**，初始基线丢失。评估过三个方案：

| 方案 | 做法 | 结论 |
|---|---|---|
| **C（就地取旧值）** | 覆写前把旧值摘出来传给 diff 重建 | ❌ **不成立**。基线仍被推进，第二次保存的比较基准变成"上一次的值"，改回原值照样多出一条 |
| **F（加列存基线）** | 在 base 表上加 `origin_cbfbm/origin_cbfmc` | ❌ 改表结构，迁移与回填成本高，收益与 A 相同 |
| **A（不覆写）** | base 只保留任务态字段同步，显示/搜索改取 result | ✅ **采用**。基线天然稳定，净差异语义自动成立 |

**A 的代价与配套**：base 的 `cbfbm/cbfmc` 从此是基线值，而用户改了名就该在列表看到新名 ⇒ 必须同时改 `task.py` 的**显示**（A2）与**搜索**（A3）。这两处不配套改，会出现"列表显示旧名、按新名搜不到"的新故障。

> ⛔ **A3 的写法有硬约束**：不能写成 `in_(select(...))` 子查询。全局 `with_loader_criteria`（区域/租户 scope 过滤）会**二次注入到子查询里**，命中集合被静默缩小。必须先查出 Python 列表再 `in_()`。详见 skill `sqlalchemy-loader-criteria-subquery`。

### 11.3 差异不对称：为什么只能"手工补"，以及顺序硬约束

直觉上应该把 `result_status` 加进 `_rebuild_diffs` 的 `contractor_fields` 让它自动比对。**实测不可行**：`survey_cbf_base` 表**根本没有 `result_status` 列**（只有任务态 `task_status`），`getattr(base, "result_status")` 会直接抛 `AttributeError`。

因此与 `deregister_contractor` 一样只能手工补。但有两条硬约束：

1. ⛔ **必须排在 `_rebuild_contractor_diffs` 之后**。该函数开头会 `DELETE` 掉 `form_diff_entity_types`（含 `contractor`）的全部行再重算，提前插入会被清掉。
2. ⛔ **`change_id` 必须指向本次操作的变更记录**，否则差异行挂不到对应台账上。

撤回侧无需额外改动：`rollback_split_household` / `rollback_merge_household` 收尾都会再调一次 `_rebuild_contractor_diffs`，这条补进去的行随之被清掉 ⇒ **净差异语义自然成立**（已实测）。

### 13.2 ⚠️ 执行中新发现的 P0：「确认调查结果」对真实户几乎全 400

**这条不在原清单里，是本次顺藤摸到的，严重度高于清单中的任何一条。**

`_validate_confirmable`（确实走「确认调查结果」的校验链）里有这么一段：

```python
if result.cbflx == "1":
    household_heads = [m for m in members if m.is_household_head or m.yhzgx == "01"]
    if len(household_heads) != 1:
        errors.append("validation error")      # → 400 "request failed"
```

**它要求"恰好一个户主"，而判据取 `yhzgx == "01"`——可真实户主是 `02`。**

**只读量化（`scripts/_diag_confirm_head_check.py`）**

| cbflx=1 的户 | 数量 |
|---|---|
| 总数 | **179,788** |
| **现行判据能通过的** | **1** ← 全库只有 1 户 |
| 修正判据（02 或 01）能通过的 | 179,335 |
| 有成员但一个户主类码都没有 | 226 |
| 有多个户主类码 | 228 |

⇒ **17.9 万户里 17.9 万户无法「确认调查结果」**。之前第九章 T7 验的是夹具（夹具恰好带 `isHouseholdHead` 标记），所以漏掉了。

**根因与 13.4 同源**：`is_household_head` 这个字段历史上按 `01` 计算，全库 60.2 万成员里**只有 1 条为 true**。

**修法**：把"恰好一个户主 + 判据取 01"换成统一口径——

```python
# 只要这一户有成员，就一定能判出唯一户主 ⇒ "没有成员"才是唯一错误
if pick_household_head(members) is None:
    errors.append("validation error")
```

> ⚠️ **这条改动会放宽一处校验**：原来"一个户主都没标/标了多个"会拒绝确认，现在会按兜底规则自动判定通过。
> 这是用户定案口径（"还是没有就随便挑一条"）的直接推论，但请知悉。

### 13.3 口径取证：户主到底是哪个码

**唯一权威来源是字典** `nyt2539_c20_relation_to_head`（`dictionary_presets.py` + `dictionary_items` 表）：

| 码 | 字典含义 | 真实数据条数（`survey_cbf_jtcy_result.yhzgx`） |
|---|---|---|
| `01` | 本人 | **1**（且这条正是被错误代码写出来的：`is_household_head=true` 唯一那条） |
| **`02`** | **户主** | **179,790**（每户恰好一条） |
| `10` | 配偶 | 106,132 |
| `20` | 子 | 57,044 |
| `30` | 女 | 45,950 |
| `22` / `32` / `23` / `33` | 长子 / 长女 / 次子 / 次女 | 31,592 / 26,958 / 22,091 / 19,490 |

⇒ **字典与真实数据完全一致：户主 = `02`、本人 = `01`**；代码里的 `01 = 户主` 是错的。
（顺带纠正：项目记忆里原写"`02` 有 17.98 万条"，实测是 **17.979 万**，量级正确。）

**同一处错位的另一个受害者是出件**：`contract_template_service.YHZGX_MAP` 写的是
`01=户主 / 02=配偶 / 03=子女 …`（NY/T 2539 早期码序），与库内字典**整表错位** ⇒
合同「承包方家庭成员信息」表的"与承包方代表关系"列会把真实户主印成**"配偶"**、
把配偶印成裸码 `10`。
**这一项必须与户主判定一起修**，否则一旦把户主的 `yhzgx` 从 `01` 改成 `02`，
就反而把"印错"从"偶然印对"变成"稳定印错"。

### 13.4 单一口径模块（`services/relation_codes.py`）

设计要点：

1. **兜底映射直接从字典预设派生**，不再维护第二份真相：
   ```python
   FALLBACK_RELATION_LABELS = {
       code: name
       for dict_type, _n, code, name, _s, _r in NYT2539_APPENDIX_C_DICTIONARY_ITEMS
       if dict_type == RELATION_DICT_TYPE
   }
   ```
2. **判定优先级**（第一条是对定案口径的必要补充）：
   ① 显式 `is_household_head=True` → ② `02` 户主 → ③ `01` 本人 → ④ 兜底第一条。
   > ⛔ **① 为什么必须排在 ②③ 前面**：合户会把 A、B 两户各自 `02` 的户主一起带进新户，
   > 若纯按码值取"第一个 02"，就会取回**原户主**、把界面/操作里指定的新户主顶掉。
   验收断言 **H5e** 专门盯这一点。
3. **只读与就地区分**：`pick_household_head` 纯读（校验、出件、前端默认值都能用）；
   `sync_household_head_flags` 就地写（保存路径用）。
4. `normalize_non_head_relations`：把**非户主**身上残留的户主类码收敛为 `80`（其他）。
   用户报的"新户出现多个户主"就出在这里——A、B 两户的户主都带着 `02` 进了新户。
   两人相对**新户主**的关系无从推断，写"配偶/子女"都是臆造，故取字典里语义诚实的 `80 其他`。

**⛔ 使用约束（写进模块 docstring）**：凡需要判断"谁是户主"的地方一律调用本模块，
**不要再写 `== "01"` / `== "02"` 的裸比较** —— 这正是历史上口径走偏的成因。

### 13.5 ISSUE-01 方案 A：把"谁能点按钮"与"接口拦不拦"改成同源

**修复前（第十二章实证）**：已注销列表的按钮判据是 `batch.status != finished`，
而它附带的变更记录只查 `change_type == "deregister"` ⇒ 合户（写 `merge_household`）
的行会渲染出一个**必然 400** 的按钮，`changeNo=null` 是最锋利的证据。

**修复后（三层同源）**

| 层 | 修复前 | 修复后 |
|---|---|---|
| 变更记录查询 | `change_type == "deregister"` | `change_type.in_(terminal_operation_types)`（三种）且排除新户的 `created*` 记录 |
| `canRollback` | `batch.status != "finished"` | `batch.status != "finished"` **and `change is not None`** —— 与三个撤回接口开头的判据一致 |
| 前端按钮 | 写死「撤回注销」→ 一律打 `rollback-deregister` | 按 `changeType` **分流**到 `rollback-deregister` / `merge-household/rollback` / `split-household/rollback`；且 `canRollback` 额外要求"changeType 已知"（否则不知道该打哪个接口） |

`terminal_source_actions`（`{"cancelled_after_merge", "cancelled_after_split"}`）与
`terminal_operation_types` 并排定义在 `SurveyServiceBase` 上，避免第二处口径。

> **为什么 M5 要保持"直发 rollback-deregister 仍 400"这条断言**：它反证本次修的是
> **入口选择**，而不是把接口判据改松。若那天它变成 200，说明修错了方向。

### 13.6 ISSUE-07 分户对齐（以及它的前置约束）

**改动**：`split_household` 现在也会把原户 `task_status` 置 `deregistered`，与 `merge_household` 一致；
`source_before` 快照增加 `task_status / has_change / change_count / remark`，
`rollback_split_household` 据此还原（否则会出现"撤回了但列表里没有"）。

> ⛔ **前置约束（本轮最主要的设计判断）**：分户一旦对齐，原户就从主列表消失了，
> 它原来那个"打开对话框 → 点撤回分户"的入口随之失效。
> **所以 ISSUE-07 不能单独做** —— 必须与 ISSUE-01 的方案 A 同时落地，
> 让「已注销列表」的分流覆盖 `split_household`。否则等于把缺陷从合户复制到分户。
> 现在两者互为前提、一起成立：**任何让户离开待办的操作，都必须留下可到达的撤回路径。**
