# 后台接口越权访问（IDOR/BOLA）安全审计报告

- **审计日期**：2026-10-09
- **审计范围**：`backend/app/api/v1/endpoints/` 全部 24 个路由模块、约 120 个端点，以及对应的 services / repositories / db session 层鉴权链路。
- **审计方法**：静态逐文件走查。每个端点核对三件事：① 是否强制登录（`get_current_user`）；② 是否有权限位（`require_permission`）；③ 数据读取是否按「当前用户的租户 + 区域授权 + 任务归属」收口（`ensure_code_in_scope` / `ensure_task_write_permission` / `build_scoped_filter`，或 ORM 全局租户过滤器）。

---

## 一、总体结论

系统有一套设计良好的**三层防线**：

1. **ORM 全局过滤器**（`db/session.py::do_orm_execute`）：所有继承 `TenantScopedMixin` 的业务模型（survey / data_export / data_import / request_case / cbht 等全部业务表）的每条 SELECT 都自动叠加「系统授权区域 ∩ 用户租户 ∩ 用户区域授权」过滤；写入（before_flush）也会校验归属。
2. **Service 层显式闸门**：`ensure_code_in_scope`（区域前缀 + 租户）、`ensure_task_write_permission`（任务归属）、`_ensure_batch_assigner`（分配权）、`_ensure_batch_manager`（结束批次）等，覆盖了调查、附件、委托书、变更记录、合同渲染等主链路。
3. **端点层权限位**：除白名单外全部端点都要求登录 + 功能权限。

**但存在 2 个高危、4 个中危问题需要整改**，详见下文。

---

## 二、发现的问题

### 🔴 高危 H1：JWT 密钥为硬编码默认值 —— 可伪造任意身份（含平台管理员）

- **位置**：`app/core/config.py:39` `jwt_secret_key: str = "replace-this-in-production"`；`app/core/security.py::create_access_token`。
- **事实**：`backend/` 下**没有 `.env` 文件**，全仓库（含安装脚本）也没有任何生成/注入 JWT_SECRET_KEY 的逻辑，因此运行中的后端就是用这个公开默认密钥签发 token。
- **攻击路径**：任何知道代码的人可自行签发 `{"sub":"1","exp":…,"type":"access"}`（HS256）→ 直接以 `user_id=1`（平台管理员，data_scope=all）通过 `get_current_user`，**读取/修改全部租户全部数据**。这是对「A 看 B 数据」的最高级越权：不需要猜 B，直接变成系统管理员。
- **修复建议**：
  1. 启动时若 `jwt_secret_key` 等于默认值则**拒绝启动**（fail-fast），并在 `scripts/install.ps1` / `start-backend.cmd` 里生成随机密钥写入 `.env`；
  2. 更换密钥后所有旧 token 自动失效（无副作用，8 小时过期）。

### 🔴 高危 H2：`/api/v1/license/*` 完全无鉴权 —— 未认证即可替换授权文件

- **位置**：`app/api/v1/endpoints/license.py`（4 个端点均**无** `get_current_user` 依赖）+ `app/core/license/middleware.py` 的 `_API_WHITELIST` 把 `/api/v1/license` 整个前缀放行。
- **攻击路径**（无需任何账号）：
  - `POST /api/v1/license/upload` → **覆盖 `storage/license.dat`**，可致全系统 403（拒绝服务），或部署攻击者自制的授权文件；
  - `POST /api/v1/license/reload` → 强制重载；
  - `GET /api/v1/license/machine-code` → 泄露机器指纹（为伪造授权提供输入）。
- **连带影响**：系统级 ORM 过滤的第一层（`license_validator.get_authorized_region_code()`）依赖授权文件，授权文件被替换会直接改变全系统的数据可见范围。
- **修复建议**：白名单只放行 `GET /license/status`（未授权时前端要展示提示）；`upload`/`reload`/`machine-code` 至少加 `get_current_user` + 管理员权限。登录接口本身在白名单内，不存在「license 失效导致管理员无法登录来修授权」的死锁，加鉴权是安全的。

### 🟠 中危 M1：`/data-exports/{export_id}/download` 缺显式归属校验

- **位置**：`app/api/v1/endpoints/data_export.py:64-85`。`db.get(DataExport, export_id)` 后直接回传 ZIP（承包方清册 + 家庭成员 CSV，含大量个人信息）。
- **现状**：同文件的 `clear_export` / `delete_export` 都调了 `data_export_service._tenant_check`（403），**唯独 download 没有**。目前跨租户/跨区域靠 ORM 全局过滤器兜底（越权行会 404），但：
  - 这属于对隐式过滤的依赖，将来若模型漏继承 mixin 或查询加了 `skip_tenant_scope` 就会裸奔；
  - `data_scope=all` 的账号可下载任意租户产物（是否符合预期需业务确认）。
- **修复建议**：download 与 clear/delete 同口径：先 `_tenant_check`，再 `ensure_region_in_scope(export.region_code)`，越权时返回 403 而非 404。

### 🟠 中危 M2：地籍调查表批量导出任务无归属校验

- **位置**：`app/api/v1/endpoints/contractor.py:148-177` + `services/cadastral_export_service.py::get_progress/get_archive`。
- **现状**：任务存于进程内存 dict（key 为 uuid4），`get_progress` / `get_archive` 不校验「任务是不是当前用户创建的」。zip 内容虽按创建人权限范围渲染，但任何有 `contractors.view` 的用户**只要拿到（或遍历泄露）task_id 即可下载他人导出的整村地籍调查表 Word 包**。
- **修复建议**：任务记录里已有 `user_id`，`get_progress/get_archive` 增加 `user_id == current_user.id or data_scope=='all'` 校验；或把 task_id 与用户绑定做签名。`raster_publish.py /progress/{task_id}` 是同一模式，一并处理。

### 🟠 中危 M3：用户管理接口无租户边界 —— 可横向看到全系统用户、可重置平台管理员密码

- **位置**：`app/api/v1/endpoints/user.py` + `repositories/user_repository.py::list_users`（User 模型不继承 TenantScopedMixin，service 也未按调用者过滤）。
- **现状**：
  - `GET /users`：任何有 `users.view` 的用户可列出**所有租户**的用户名、姓名、角色、区域（信息泄露面）；
  - `POST /users/{id}/reset-password`：任何有 `users.manage` 的用户可重置**任意**用户（含平台管理员）的密码 → 水平越权 + 垂直提权链（改了管理员密码即完全接管）。
- **修复建议**：① 非平台管理员（data_scope≠all）调用用户管理接口时，列表强制按 `User.tenant_code == 当前租户` 过滤；② `reset-password`/`update_user`/`delete_user` 拒绝操作 `data_scope='all'` 的账号（仅平台管理员可管理平台管理员）。

### 🟠 中危 M4：登录接口无失败锁定 / 限流

- **位置**：`app/services/auth_service.py::login`。密码错误仅返回 401，无计数、无延迟、无验证码；`/api/v1/auth` 在中间件白名单内且无需 license 有效。
- **风险**：可对任意用户名在线爆破（8 小时长 token 也放大了口令被猜中后的停留时间）。
- **修复建议**：按用户名+IP 做失败计数（如 5 次失败锁 10 分钟，Redis 16379 已在栈内可用），并记录失败日志。

### 🟡 低危 / 加固建议

| # | 位置 | 问题 | 建议 |
|---|------|------|------|
| L1 | `contractors/{code}/cadastral-survey.docx`、部分只读接口 | 未做显式 `ensure_code_in_scope`，只靠 ORM 隐式过滤（当前实际安全，越权行查不到 → 404） | 与兄弟接口统一显式校验，防止未来新增非 scoped 模型或误用 `skip_tenant_scope` 时裸奔 |
| L2 | `main.py` | 生产环境开放 `/docs`、`/redoc`，接口清单/参数结构对未认证用户可见 | 生产关闭或加鉴权 |
| L3 | `app_updates.py` | 免登录是**设计决定**（文档已注明，文件名做了目录穿越校验），但 bundle 本体无服务端签名，明文 HTTP 部署时可被中间人替换 | 部署走 HTTPS；客户端已校验 sha256，可保持现状 |

| L5 | token 有效期 8 小时 | 无刷新机制、无服务端吊销 | 可接受；若要收紧可缩短+refresh token |

## 四、修复优先级

1. **立即**（H1）：生成并配置真实 JWT 密钥 + 启动 fail-fast。一行配置解决最大的洞。
2. **本周**（H2）：license 写操作加鉴权；M1 download 加 `_tenant_check`；M2 导出任务加归属校验。
3. **下个迭代**（M3、M4 + L1~L2）：用户管理租户边界与提权链封堵、登录限流、docx 下载显式校验、生产关 docs。
4. **回归**：按项目惯例，权限改动后跑 `backend-permission-verify` 四层验收，新增闸门各配一条 403 用例。

> 附注：本次审计为静态走查（读代码核对闸门），未做在线重放验证。如需「真请求证明」级别的验收（A 用户 token 打 B 数据必须 403），可按 `backend-permission-verify` 的四层范式补一组离线验收脚本，逐条固化本文 H/M 级问题。

## 六、第二轮检查：弱口令 + SQL 注入（2026-10-09 15:40）

### 结论

**SQL 注入：未发现可利用点**。全仓库原生 SQL 共 4 处，逐一核查：

| 位置 | 结论 |
|------|------|
| `repositories/land_parcel_repository.py`（5 个原生 SQL） | ✅ 用户值全部绑定参数（`:cbfbm`、`:dkbm_i`、`:scope_*`），拼接部分只有表名/别名等代码常量；且自带区域 scope（防越权） |
| `db/sequences.py:112,143` | ✅ `table/column/序列名` 全部来自代码内 `BUSINESS_SEQUENCES` 常量注册表 |
| `data_import/helpers.py:255`、`row_import.py:524` | ✅ 表名经 `_GEOMETRY_TABLES` frozenset 白名单 / 调用方传常量；SRID 来自配置 int |
| `nyt2539_export_service._write_sqlite`（SQLite DDL） | ✅ 表名/列名来自代码常量 `_ALL_LAYERS`，行值走 `?` 占位 |

`data_access_service.get_data_permission_sql`（f-string 拼接式）当前**无调用方**，已加「调用方必须传常量」的审计注释，建议后续删除。

其他核查：XML 解析（stdlib ElementTree/lxml）无外部实体注入面；附件下载走 `FileResponse(filename=...)`（`Content-Disposition: attachment`），存储型 XSS 面闭合；`ilike("%keyword%")` 存在 LIKE 通配符注入但仅影响列表筛选宽度（低危，可接受）。
